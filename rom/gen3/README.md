# rom/gen3

This folder holds what we add to pokeemerald-expansion and the changes we make to it, without a fork (ADR 0007).

- `build.json`: the pinned upstream (repository, tag, commit), the SHA1 of the US Emerald dump that the BPS patch starts from, and the cap on make jobs.
- `src/`, `include/`, `test/`: our own C files. The build copies them into the same folders of the upstream tree, where the Makefile's wildcards find them. Their names start with `replay_`. A file that upstream already tracks is an error.
- `patches/series`: the changes to upstream files, one patch per line, applied in order. Each `NNNN-name.patch` is a `git diff` with its reason in a few lines above the first `diff --git`. A patch never adds a file; new files go into `src/`, `include/` or `test/`.
- `shot/replay_shot.c`: the screenshot tool, a host program that `npm run rom:shots` builds against libmgba. The build never copies it into the upstream tree.
- `include/replay_slot.h`: the layout of the replay slot (ADR 0008 for the ROM image, ADR 0009 for the module). `scripts/rom-slot.ts` reads its `REPLAY_SLOT_*` defines, so the header is the one source of the layout.

The build scripts are `scripts/rom-*.ts`. The upstream tree lives in `.cache/rom/expansion/` and the outputs in `build/rom/`. Git ignores both.

## Building

Each command is a heavy check on devbox, so run it alone and in the background.

- `npm run rom:build` clones the pinned tag into `.cache/rom/expansion/` if it is missing, applies `patches/series`, copies our files, runs make and writes the outputs to `build/rom/`: the ROM, the BPS patch against your dump, `replay-slot.json` and `build-info.json`. `npm run rom:build -- --clean` starts from a fresh tree.
- `npm run rom:repro` runs two clean builds, the second in a fresh worktree, and fails unless the ROM, patch and slot description are equal. It takes as long as two builds, about 90 minutes on devbox.
- `npm run rom:clean` empties `build/rom/` and drops the build products from the tree. `npm run rom:clean -- --all` deletes the tree as well, so the next build clones it again.
- `npm run rom:check` runs the expansion's own `make check` with our tests in the tree, filtered to the tests whose names start with `Replay`. `npm run rom:check -- <filter>` takes another filter: a name prefix, `*` and an infix, or a test file such as `test/battle/ability/intimidate.c`. The first run builds the test objects in `build/emerald-test/` of the tree, about 20 minutes on devbox; later runs build only what changed. The log goes to `build/rom/check.log`.

The build reads your US Emerald dump from `~/roms/Pokemon - Emerald Version (USA, Europe).gba`, or from the path in `IRV_BASE_ROM`, and checks its SHA1 against `build.json`. It stops when the ARM toolchain is missing, and prints the `apt-get` line that installs it. It also stops when less than 3 GiB of memory is free.

The build deletes files only inside `.cache/rom/` and `build/rom/`. A script that only reads the pinned tree can take it from `IRV_EXPANSION_TREE` (an absolute path) instead.

## Testing the ROM interpreter

The ROM interpreter (`src/replay_interpreter.c`, `src/replay_setup.c`) plays an instruction stream (`include/replay_stream.h`) in a recorded link battle. Four patches hook it in:

- 0001 hands it the battle main loop.
- 0002 hides the near side's HP numbers while a replay runs.
- 0003 makes the ROM boot straight into it. `src/replay_boot.c` starts the stream in the replay slot with no save file and no button press. When the ROM refuses the slot or its stream, `src/replay_refusal.c` shows the refusal screen: the reason in text on a dark red backdrop, with the error's number.
- 0004 makes the recorded controllers draw each side's trainer pic from the stream. They ask `Replay_GetTrainerPic` (`src/replay_setup.c`), which gives their own pick in every other battle.

`src/replay_stream_check.c` checks the whole stream before a battle starts, in two passes: first each instruction alone, then the order rules in the header comment of `include/replay_stream.h` (no MOVE before its user is sent out, no HP for a side whose battler fainted, and the rest). The first pass refuses a trainer pic the side cannot draw as `TEAM`: the near side draws a back pic, which only 11 pics have, and the far side a front pic, which POKEDUDE and OLD_MAN lack. The encoder refuses the same pics (`src/gen3/stream/teams.ts`). `src/replay_stream.c` reads the stream. The ops share `include/replay_ops.h` with the main loop:

- END, TURN, PRINT, FLUSH_TEXT_BOX, INTRO and SEND_OUT: the main loop, `src/replay_interpreter.c`. FLUSH_TEXT_BOX empties the text box as a battle script's `flushtextbox` does, before each later hit of a multi-hit move; ITEM_POP_UP starts with the same flush.
- MOVE, HIT, HP, FAINT and SHOW_MON: `src/replay_ops_damage.c`. In version 3 of the stream, MOVE has five bytes: user side, target side, the move (u16) and `animTurn` (u8), the turn the game's move animations read to choose between their two scripts (`gAnimMoveTurn`). The validator takes any value, and MOVE hands it to the controller unchanged, as the engine does. The backend picks the turn the engine would pass (`src/gen3/translate/anim-turn.ts`). MOVE Transform first marks its user as transformed and gives it the personality and shininess of the target's battle mon, the copy of its party mon, as `Cmd_transformdataexecution` does. The animation then draws the copy with the target's colours and Spinda's spots, and a later reload of the sprite, after a substitute fades, draws it the same way. SWITCH_IN clears all three. SHOW_MON (version 3, side only) shows the mon's sprite again with the controller's sprite invisibility command and no animation. Fly, Dig, Dive and Bounce hide their user on the charge turn, and their hit shows it again. When the hit turn plays no move animation (a miss, Protect, a full paralysis), the engine shows the user with that command (`MoveEndAttackerVisible`), and the backend writes SHOW_MON at the same point (`src/gen3/translate/hidden.ts`). A visible mon stays as it is.
- WITHDRAW and SWITCH_IN: `src/replay_ops_switch.c`. A mon that enters takes the species of its team table again, so a Castform that left in its Sunny form comes back as Castform, as in the game.
- STATUS, STAT, ITEM, ITEM_POP_UP and FORM_CHANGE: `src/replay_ops_state.c`. FORM_CHANGE (version 3, side and species) gives the mon a new species and plays the game's form change animation (`B_ANIM_FORM_CHANGE`), as Castform's Forecast does. The ability pop-up and the line "transformed!" come as ABILITY and PRINT around it.
- ANIM, with its table of the game's animations, and TRAP_TURN: `src/replay_anims.c`
- WEATHER, VOLATILE and ABILITY: `src/replay_ops_field.c`

The end comes from `src/replay_outro.c`. A PRINT right before the END of a win, the win line, starts the victory music first, for a win of either side; a tie keeps the battle music. END counts as done and finished at once. On the next frame the outro takes over the battle main loop. Every mon still out goes back into its ball, the loser's first. The winner's trainer slides in, the scene holds for two seconds, and the screen and the music fade to black. A tie or an unknown end slides no trainer in. END stops the low-HP beep for every outcome: the game stops it at a win and when it leaves a battle, and the outro stays in the battle. The ROM then holds the black screen. A held B never leaves the replay. The game quits a recorded battle on B until its playback counts as finished (`BattleMainCB2`), and the interpreter marks it finished when it takes over the battle, so the replay plays to END and the outro plays out.

`src/replay_setup.c` fills both parties from the stream. A team member that the replay never reveals gets a slot: the empty slots up to the trainer's team size, at most 6, take a copy of the side's first revealed mon, so the intro's ball display shows a ball for each team member.

After a faint the expansion plays its KO animation (`B_ANIMATE_MON_AFTER_KO`). The interpreter waits for it, as the battle script's `waitanimation` does: the faint line that follows FAINT prints while it runs, and every other op waits for its end. FAINT sets the battler's HP to 0 first, as the game's Explosion does for its user, so a later faint on the other side starts no KO animation on a fainted mon.

The tests in `test/replay_*.c` use `include/test/replay_test.h`:

- `REPLAY_TEST(name)` writes a stream in its `STREAM` block with the `ReplayStream_*` writer (`test/replay_stream_writer.c`), queues the events it expects in `SCENE` with upstream's matchers (`MESSAGE`, `HP_BAR`, `ANIMATION` and the rest), and checks the battle in `THEN`, after END and before the test leaves the battle, so the parties, `gBattleStruct` and the sprites are still there. A test that calls `ReplayTest_PlayOutro()` in `STREAM` runs `THEN` after the outro instead, and `ReplayTest_ProgressAtOutroStart()` and `ReplayTest_LowHpBeepAtOutroStart()` give the progress and the low-HP beep on the outro's first frame. A test that calls `ReplayTest_HoldB()` holds B on every frame from the takeover to END, through the hook `ReplayTest_AtFrame`. The runner fails a test whose battle leaves before END.
- `ReplayTest_KOAnimsAtOpStart(op)` returns the KO animation counter at the start of op `op`, counted from 0, for the first 32 ops of the stream. The interpreter records it through the hook `ReplayTest_AtOpStart`, which exists in test builds (`TESTING`). `ReplayTest_TrainerSpriteAtOpStart(op, side)` returns a side's trainer sprite at the same moment: its images, pic and palette tag. A SEND_OUT frees that sprite, so a test reads it at the start of the first SEND_OUT. `ReplayTest_AnimMoveTurnAtOpStart(op)` returns `gAnimMoveTurn` at the same moment, so at the start of the op after a MOVE it holds the turn that MOVE's animation read. `ReplayStream_MoveOnAnimTurn` writes a MOVE with a turn, and `ReplayStream_Move` writes turn 0.
- `test/replay_anim_turns.c` also holds upstream battle tests (`SINGLE_BATTLE_TEST`) whose names start with `Replay: engine:`. Each plays one case in the expansion's own battle engine, such as Curse by a mon that is not a Ghost or Swallow after two Stockpiles, and reads the turn the engine passed to the move animation. Each test makes its move the battle's last move animation in one of three ways: the other mon is faster and its Celebrate comes first; the move knocks it out, as Bide's unleash does; or the other side switches and makes no move, as in the Pursuit test. The backend's choice of `animTurn` follows them. Two more engine tests pin an order: Skull Bash plays its charge animation before its line "tucked in its head!", and Future Sight hits with its animation after its user fainted, before the replacement comes in.
- `test/replay_hidden.c` checks the sprite of a hidden user. Headless tests skip move animations, so its tests switch them on with upstream's `FORCE_MOVE_ANIM(TRUE)` (in `STREAM` for a `REPLAY_TEST`) and off again in `THEN`, and read the sprite's `invisible` flag in `THEN`. The engine tests show that Fly's charge hides its user, that a hit turn into Protect, into an immunity or stopped by a full paralysis shows it again, that Gust on the Fly user leaves it hidden, and that the Fly user stays hidden into its hit turn: a faster foe's Explosion misses it and ends the battle before the hit. The replay tests show that MOVE's Fly charge hides the user and that SHOW_MON shows it.
- `test/replay_transform.c` checks Transform's copy. Headless tests play Transform's animation (upstream plays it even then), so they read the copy's palette and pic in `THEN`: the copy takes a shiny target's palette in Transform's tint on both sides, a Spinda target's personality and spots, and the same palette after its substitute fades; the mon that switches in next is no copy.
- A plain `TEST` whose name starts with `Replay:` checks a refusal with `Replay_Validate`, without a battle. The order cases in `test/replay_refuse_order.c` start with `Replay: order:`. `src/gen3/stream/order.test.ts` holds the same cases with the same ops, side operands and verdicts, and fails when a case is on one side only. `test/replay_refusal.c` checks that each refused code has a text of its own on the refusal screen and that each text fits the screen's window.

## Screenshots

`npm run rom:shots` plays streams in the built ROM from boot to END in headless mGBA and checks named scenes in the frames. It needs a ROM from `npm run rom:build` and `sudo apt-get install libmgba-dev`, and builds `shot/replay_shot.c` into `build/rom/shot/` on its first run. It is a heavy check: run it alone.

With no name it plays test replay 994052 through the battle script and the Gen 3 game backend. `npm run rom:shots -- 994086 hand-made` plays the named streams instead: a test replay by its id, or `hand-made`, a short battle written with the stream encoder (the intro, both send-outs, a move, an HP change, a status, a switch, a faint and the win line). `send-outs` plays the 17 battles of `scripts/wasm-sendouts.ts`, `send-outs-1` to `send-outs-17`, which send out one species for each front animation and each back set the pinned species tables hold. A near send-out plays the function of its back set that the drawn nature picks, so the battles do not play every back function. Two refusals follow each time. The built ROM's empty slot is refused as `EMPTY`, and the hand-made battle with the first unknown stream version, 4, is refused as `VERSION` (the run `version-4`). Each refusal must show text on the refusal backdrop. With `hand-made` named, a third run, `hand-made-b`, plays the hand-made battle again with B held from the first frame, and must show every scene of `hand-made`. A held B counts as a press on its first frame only, and the hand-made battle prints no text on frame 1, so its frames equal those of `hand-made`.

The tool takes a frame at each scene of `scripts/rom-shot-scenes.ts`, and `scripts/rom-shot-probes.ts` checks it with numbers: two frames differ, the near HP digit area shows only the healthbox background, the far HP bar fills the pixels the engine fills for the logged HP, the text box holds the win line, 150 frames after END a near winner's trainer stands where the intro drew it, pixel for pixel, while a far winner's trainer stands where its slide ends, 32 pixels right of where the intro drew it (the field behind it differs between the two places, so the probe slides the intro's trainer up to 16 pixels each way over the region and finds the best match at the slide's end; a trainer still on its way in stands 2 pixels right for each frame its slide has left), after a tie the text box still shows the last line, and each side's ball display in the intro shows one ball per team member, up to 6, with no empty cell between them. The run fails when a scene fails, when an op waits 3600 frames, or when the replay stops short of END. 994052 and `hand-made` must show every scene; for another replay the output and `report.json` list each scene its stream lacks. The tool reads the interpreter's progress at the offsets in `include/replay_progress.h`, which also holds the refusal screen's colour. The frames (PPM), the ROMs with their streams and `report.json` go to `build/rom/shots/`. Git ignores that folder, and the tree spec refuses a frame anywhere in the tree.

## The WebAssembly build

The WebAssembly build (#35, #43) compiles the expansion with our C files to a WebAssembly module that runs in the browser without an emulator. `docs/wasm-spike.md` holds the results. The build lives in `wasm/` and reads the tree that `npm run rom:build` leaves; the ROM build never sees any of it.

- `wasm/wasm.json`: the pinned Emscripten release, the tree files the module leaves out, and per-file defines and compiler flags.
- `wasm/src/`: the glue, our C files for the module only. It blocks in `VBlankIntrWait`, has our platform layer run the frame, raises the interrupts, hands frames and sound to JavaScript, and stubs flash, the clock, the link cable and multiboot. A run that must not go on stops in `irv_wasm_stop.c`, with a line that `wasm:run` and the page show.
- `wasm/include/`: shadow headers. Each one shares a name with an upstream header, comes first on the include path, includes upstream's with `#include_next`, and then adds to it. Most add defines. `irv_wasm_sound.h` is our own.
- `wasm/patches/series`: overlay patches. The build copies an upstream file into `build/wasm/overlay/`, applies its patch there, and compiles the copy. Each change sits under `#ifdef IRV_WASM`, and each patch carries its reason above `diff --git`, as the ROM's patches do.
- `wasm/layer/`: our platform layer (#43), the C code that stands in for the GBA's hardware: BIOS calls, DMA, the interrupts, the frame driver, the renderer and the sound. It compiles with the glue, and `wasm/layer/host/` holds the native harness that runs the same files in the specs.

The platform layer is ours, under the repository's MIT licence. Until #43 the build fetched a borrowed one from pokeemerald-multiplatform; it fetches nothing now. The module, its patch, the frames and anything else built from your dump never enter git.

Each command is a heavy check on devbox, so run it alone and in the background:

1. `npm run wasm:build -- --compile` compiles the kept tree files, the overlay copies, the glue and our platform layer at `-O2` into `build/wasm/obj/` (about 5 minutes).
2. `npm run wasm:convert` turns the 544 ARM data objects of the ROM build (battle, animation and event scripts, songs) into WebAssembly objects in `build/wasm/asm/`. It is needed again only when the data changes.
3. `npm run wasm:build -- --link` compiles the glue and our platform layer and links `build/wasm/irv-emerald.js` and `irv-emerald.wasm`. It turns each integer division and remainder of the module into a call of the glue's helper, which returns the GBA's result where WebAssembly would trap (`scripts/wasm-divide.ts`, about 20 seconds). Then it writes the module patch `irv-emerald-wasm.bps` from your dump. `--patch` writes the patch alone.
4. `npm run wasm:run -- hand-made 994052` plays streams in the module in Node and checks the scenes of `rom:shots`. `--all` adds every test replay after the streams you name. Each stream gets a fresh module in a process of its own, so a stream that traps, hangs or misses a scene fails alone and the run plays the rest. The report gives each stream's END frame or its failure (a trap with the frames before it) and ends on the count of passed and failed streams. The command exits with 1 when a stream failed. It writes its frames and `report.json` to `build/wasm/run/`. `--against-baseline` compares every stream the baseline holds and marks the others "no baseline"; it refuses to start when the baseline holds none of them.

`npm run wasm:census` compiles every tree file once at `-O0` and sorts the failures by class; the spike used it to find what the build had to change. It applies no overlay patch, so a file that one fixes, `random.c` among them, still fails there. Emscripten installs outside the repository, under `~/tools/emsdk`; `EMSDK` names another place.

## Adding a patch

1. Edit the upstream file in `.cache/rom/expansion/`.
2. Run `git -C .cache/rom/expansion diff -- <files> > rom/gen3/patches/0001-<name>.patch`.
3. Write the reason at the top of the patch, above `diff --git`.
4. Add the file name to `patches/series`.

Keep the patches few and small. New behaviour goes into our own files (AGENTS.md).
