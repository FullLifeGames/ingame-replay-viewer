# The WebAssembly spike (#35)

Milestone 1b asked one question: can the pinned pokeemerald-expansion, with our C files, run in the browser as WebAssembly instead of inside mGBA? The spike ran in wave 3, lane b, from 21 to 22 November 2026: nine builder steps of a ten-step box, a review, and two fix steps for its findings. This page records what it found. The wave 3 gate (22.11.2026) chose to ship it in milestone 2, with a platform layer of our own (#43).

## Verdict

The spike works. The WebAssembly build of the pinned expansion with our C files plays the hand-made stream at 1x and 994052 at fast from boot to END in Chromium on devbox, with sound. In the Node harness its frames pass the same 13 scenes as mGBA's, and in Chromium it reaches END at the same frames as in Node. In Chromium it runs about as fast as mGBA's page at fast-forward, and compressed it downloads 0.8 MB less.

Two things stood between it and a public build in wave 3: a platform layer we may ship, which #43 built in wave 4, and the module patch's assets, which the wave 3 gate accepted under ADR 0002 as amended.

## What the build is

- Emscripten 7.0.0 (pinned in `rom/gen3/wasm/wasm.json`, installed in an emsdk checkout) compiles 386 C files, the tree's, our replay files among them and eight from patched copies. All 386 compile at `-O2`, and so do the 26 C files of our glue and our platform layer. In wave 3 the build also compiled six platform files borrowed from pokeemerald-multiplatform; #43 replaced them all, and the build fetches nothing of that repository now. The census before any fix had 373 of 395 passing. It applies no overlay patch, so it still counts the files that one fixes, `random.c` among them, as failing.
- The 544 data objects that the ROM build assembles with ARM `as` (battle scripts, animation scripts, event scripts, songs) go through a converter (`scripts/wasm-convert.ts`). It reads each ARM ELF object and writes LLVM's WebAssembly assembly with the same bytes and relocations. All 544 assemble.
- The GBA's addresses map one to one into linear memory: EWRAM at 0x02000000, IO at 0x04000000, VRAM at 0x06000000, static data from 0x08000000, where the ROM would sit. The memory is a fixed 256 MB.
- Our platform layer (`rom/gen3/wasm/layer/`, #43: 17 C files and 11 headers) stands in for the GBA's hardware. It makes the BIOS calls, runs DMA and the interrupts, drives the display line by line and draws each line: text and affine backgrounds, sprites, windows, blending and mosaic. It also plays the sound: the game's music players and the PCM mixer (`irv_mp2k_*.c`, written from a functional spec of the game's sound engine) and the four PSG channels, synthesised from the sound registers (`irv_psg.c`). We wrote it from GBATEK and the game's own sources. It includes no header of the expansion, so a native harness (`layer/host/`) runs the same files in the specs, in CI too.
- Our glue (`rom/gen3/wasm/src/`, twelve files, 901 lines) blocks in `VBlankIntrWait`, has our layer run the frame, passes each interrupt to the game's handler, and hands each frame and its sound to JavaScript. It also stubs flash, the clock, the link cable and multiboot. A run may call four of the stubs, the ones `InitRFU` calls at boot, which `irv_wasm_stub_list.h` lists (#46). A call to any other stub stops the run with the stub's name, and `wasm:run` and the page show it. A failed assert stops the run with its file, line and expression, and a warning only prints (#61). A mixer that runs at another rate than the page expects stops the run too. All three go through one stop, `irv_wasm_stop.c`. The glue's compile checks the offset and size of every field that our layer's structs share with the expansion's. `irv_wasm_divide.c` holds a helper for each integer division and remainder, which the build calls in place of WebAssembly's ops (see "The class nothing warns about").
- The page (`src/web/index.html`, the viewer since wave 4) rebuilds the module from your dump with a BPS patch, the way the emulator page rebuilds the ROM. A worker runs the game and hands each frame over through two buffers, so the page never copies a frame the worker is still writing (#48). The page allows the worker its frames at 1x, 2x or fast, and an audio worklet plays its sound.

## What works

### Graphics

All 13 scenes of `rom:shots` pass in the Node harness (`npm run wasm:run`) on hand-made and on 994052, with the same probes and thresholds as on mGBA. Both refusals show their colour and name their reason in text (#30): the refused frame of each equals mGBA's to the pixel.

Our renderer (#43) draws every frame. `npm run wasm:diff` counts the pixels where a scene frame of the module differs from mGBA's. A refused run writes no scene frame, so `wasm:diff` compares its final frame, the refusal screen; on `empty-slot` and `version-4` it matches mGBA's to the pixel. With our renderer and the two fixes to the game's drawing code below (`bg.c`, `text.c`), most scene frames of both streams match mGBA's to the pixel. `outro` is one of them on both streams: 150 frames after END the module's frame equals mGBA's, with the winner's trainer slid in, the text box and the field. The others catch a sprite in motion, and the two engines stand a few frames apart there (see Timing): `intro-before` (882 pixels) and `weather-start` (20,849) on both streams, as with the borrowed renderer in wave 3; `first-faint` (791 on 994052, 1,584 on hand-made), where the faint slide stands a step apart; and on hand-made `win` (803), where the player's Magneton stands at another point of its motion. Hand-made's `first-faint` and `win` matched in wave 4's step B4 and differ since the shot tool's mGBA runs on the module's fixed clock (see Frames to END), with our frames unchanged. Stage 3's merged tree (stream format 2, the outro) gave the same counts. In #43's first part the module of wave 3 with the borrowed renderer drew all 40 scene frames of both streams byte for byte as ours does, so each count above comes from where mGBA stands, and our layer adds none. Stage 5's two new streams differ in one scene each. On 995161's `first-faint` (1,683 pixels) the near Exeggutor's back sprite runs 5 frames behind mGBA's: the module's frame 5 frames later equals mGBA's scene frame inside the sprite. On 993907's `first-move` (2,647 pixels) the Reflect wall is a semi-transparent sprite, and every differing pixel is the wall's alpha blend (EVA 13, EVB 3), which our layer computes on 5-bit channels and mGBA on 8-bit ones (see the next paragraph).

`npm run wasm:oracle` checks the renderer against mGBA without that gap. The shot tool dumps mGBA's own video state every 60 frames; the oracle draws each state with our layer in the native harness and compares the result with mGBA's frame of the same instant. On stage 3's merged tree each sampled state matched its mGBA frame: 48 of 48 on hand-made and 682 of 682 on 994052. mGBA blends its colours on 8-bit channels, so the oracle holds a blended pixel against mGBA's arithmetic on our choice of layers and coefficients. It also holds the pixel our layer drew against GBATEK's 5-bit arithmetic on the same choice, which the blend specs pin. At no frame's end did either stream show an affine background, mosaic, WIN1 or a 256-colour tile (#43's census), and no sampled state brightens (BLDCNT mode 2), so only their specs check those.

### Sound

Sound plays, from our own sequencer, mixer and PSG. The module mixes 704 left and right pairs per frame at 42048 Hz, the expansion's own top rate, in Node and in Chromium, and hands each frame's pairs to the page at the end of the game's `SoundMain`. In Chromium the worker writes 0.992 of the mixer's rate into the audio ring at 1x, and the worklet reads 0.991 (B9's e2e on hand-made, after our mixer took over; at 2x 1.016 and 0.999). At 2x the page plays the game's sound at double pace and pitch; at fast it stays silent.

Our mixer adds the two FIFOs and the PSG in GBATEK's output units, adds the bias, clips to 10 bits and maps the result to -1..1. That is the GBA's own level, and wave 4 keeps it (S4-10 in the wave 4 booking): RMS 0.148 on hand-made and 0.158 on 994052. Hand-made peaks at 0.86, and on 994052 8 of 57.7 million samples reach the clip. One constant in the mixer's output sets another level. The mixer that wave 3 borrowed played about 8 times quieter, and over 30-frame windows of hand-made its output correlated with ours at 0.55 to 0.78, ours one frame ahead because the module hands each frame over at the end of `SoundMain`, no longer at line 150. On the stage 4 page, at a load of 5 to 7 from another session, the spike e2e reached END at 2916 at 1x with a switch to 2x and back, and at 2916 at 2x; the worker wrote 0.992 of the mixer's rate and the worklet played 0.930 at 1x, 1.016 and 0.979 at 2x. Over the 1x run with its switches the worklet skipped 491,524 samples and ran dry 10 times.

At the win line the BGM player switches from the battle song (8 tracks) to `MUS_VICTORY_TRAINER` (9 tracks): at frame 2829 on hand-made and 40884 on 994052, 87 and 97 frames before END. `npm run wasm:run` prints the songs and the level by second up to the end of the outro.

In B6 the worklet read about 3 % slower than the worker wrote (0.962 against 0.992); in B7's two e2e runs the gap was 2.5 % on the dev server and none on the preview (0.998 against 0.997), each over one 5 s window. B6 suspects the clock of headless Chromium's fake output; nobody measured a real output. At B6's gap the ring filled in about half a minute, and from then on every push dropped the tail of a frame.

The worklet now caps the ring's latency at 0.2 s. When more waits, it skips the oldest samples down to 0.1 s in whole left and right pairs and counts them. It counts an underrun once for each dry spell, when the ring runs empty after the sound has started, and waits for a reserve of 1408 pairs (33 ms) before it plays and after each dry spell. While sound plays, the page's progress line ends with both counts ("The page skipped N sound samples and ran out of sound M times."). The test hook reports them too, and the e2e asserts the worker's pace and reports the worklet's. The ring's counters wrap at 2^32, so a run that plays on for hours keeps its sound.

Fix step 11's e2e ran beside another session's Playwright tests (load average 4.8 to 7.7 on six cores). At 1x the worker wrote 1.000 of the mixer's rate, and the worklet played 0.800. By END the worklet had skipped 1,142,690 samples, 13.6 s of the 48.9 s, and had missed 41,120 output frames, 0.93 s; no push overran. At 2x the worklet played 0.617 against 0.993 written. Under that load the audio thread of headless Chromium ran a fifth slow, and the cap held the latency by skipping the difference. Without the cap the ring would have filled and dropped as much.

### Timing

The page ticks at the GBA's 59.7275 frames per second. The e2e measures 1x within 5 % of that and 2x within 5 % of twice that. Fast runs the worker as fast as it goes, and at END the page leaves fast for 1x, so no core spins while the game plays on after the replay. A hidden tab gets no animation frame, so the game pauses there at 1x and 2x. When the tab comes back into view, the page resumes the tick clock, and the game goes on from where it paused. In view, the page grants the game at most half a second of frames past the frame it has reached, plus the frames owed since the page last asked. A late animation frame loses nothing. A game that stalls for longer than half a second makes up that half second as fast as it can, drops the rest and goes on at its pace. One ask pays at most one second of the frames owed since the last ask (`src/web/wasm/clock.ts`): a page in view that asks again after five seconds grants at most one second of the gap plus the half-second lead and drops the rest, so the burst fits the sound ring. The Pause button holds the game at its frame and suspends the sound; Play resumes the clock from that frame, so a pause owes no frames (#57).

### Input

The viewer presses no key, and neither page passes one to the game: mGBA's page turns input off (`toggleInput(false)`), and the module's glue sets `REG_KEYINPUT` to all keys up once at start (`irv_wasm_layout.c`). A zero there would read as every key held, and A, B, Start and Select held together make the game soft-reset.

A held B leaves the replay on screen in both builds. The replay plays as a recorded battle, and `BattleMainCB2` (`src/battle_main.c:1739`) quits a recorded battle's playback on B while `RecordedBattle_CanStopPlayback()` allows it. The interpreter marks the playback finished when it takes over the battle (#68), so B does nothing up to END and after it. A press of A or B speeds up the line a text printer is printing (`src/text.c:1338-1344`); B held from the first frame presses on no printed line, so `hand-made-b` plays frame for frame as `hand-made`. `rom:shots` and `wasm:run` hold B from the first frame in their run `hand-made-b`: the shot tool through mGBA's keys, the module's runner by writing all keys up but B to `REG_KEYINPUT` (0x04000130) before each frame. Live play (roadmap 7) needs the page to write the keys it reads there the same way.

Three things move the counts:

- Boot. mGBA spends 13 frames before the game's first frame, which the module skips: it calls `AgbMain` straight away. The refusals show it (44 against 31).
- The silent stubs before B6. Until the module had sound, every cry and fanfare that the game waits for ended at once, and in the spike's step B4 the module reached END at 2876 on hand-made and 38942 on 994052, 767 frames before mGBA. With the mixer in, the module ends 7 frames after mGBA on 994052 and 7 before it on hand-made.
- VBlank overruns. On the GBA a frame whose work runs past the next VBlank misses it and takes two. The module's work takes no display time, so its frames never overrun, which would let it finish earlier. After the 13 boot frames, the module takes 6 frames more than mGBA on hand-made and 20 more on 994052. So mGBA's overruns cost it fewer frames than something else costs the module, the mixer's timing of the cry waits being the first candidate. The spike did not measure the split.

Since #43 the shot tool stops mGBA's clock at the module's time, noon on 1 January 2000 UTC. Two oracle runs of hand-made then dumped byte-identical states and frames, and two runs of 994052 (the oracle's and `rom:shots`') reached END at the same frame. With that clock and format 1, mGBA reached END at frame 2923 on hand-made and 39629 on 994052, and the module at 2916 and 39637.

## What it means for the speed options and for #17

#35 also asks where the speed options go, mGBA's fast-forward or our own frame loop, and how #17, the patch size, gets solved.

The speed options go into our own frame loop if milestone 2 ships the module. The page already grants the worker its frames by the tick rule (`src/web/wasm/protocol.ts`), so 1x, 2x and fast are one factor each, the sound follows at 1x and 2x, and fast gives way to 1x at END. If milestone 2 keeps mGBA, the options go to mGBA's fast-forward multiplier instead. In Chromium that tops out near 314 frames per second, where the module's fast averaged 330 to 348 in B6 and B7.

The module does not solve #17. Its patch is 20.97 MB raw and 14.16 MB with brotli, against 18.39 MB and 14.49 MB for the ROM patch. Each copies under a quarter of its bytes from the dump and carries the rest itself. A visitor fetches 0.82 MB less on the WebAssembly page with gzip and 0.84 MB less with brotli, and the host's compression saves more than the switch: brotli takes 3.90 MB off the ROM patch. Per-asset extraction (below, "Nintendo's assets from the dump") is the one lever the spike found that shrinks the module patch itself, by the retail assets the expansion recompresses. The expansion's new assets stay in the patch on either route.

## Bugs the port found

Each one passed on the GBA and broke the module; each fix stays inside the WebAssembly build.

- **Struct layout.** The GBA build compiles with `-mabi=apcs-gnu`, which rounds a struct's size and alignment up to 4. wasm32 aligns each member by its own size. Our `struct ReplayProgress` came out 10 bytes under wasm32 against 12 on the GBA, and its size assert stopped 12 files. Explicit padding (`u8 padding[3]`) gives 12 on both; the ROM stayed the same. A probe of 159 structs found 35 that differ, none of them in the ARM data the converter carries. The save blocks shrink, so a save from the module would not load on a GBA, and the module turns off the one save size assert the battle reaches (`recorded_battle.c`).
- **The tilemap check in `bg.c`.** `IsTileMapOutsideWram` counts every buffer above IWRAM's end as VRAM. In the module the heap and static data sit above 0x08000000, so every background's tilemap buffer counted as outside, and the copy and fill functions skipped their writes. The text box and every window on BG0 stayed black. Patch 0005 counts only the range between IWRAM's end and 0x08000000 as outside.
- **The shift by 32 in `text.c`.** `GLYPH_COPY` computes `(1 << 32) - 1` for an 8-pixel glyph column and shifts right by 32 when a glyph starts on a tile's edge. The GBA's shift by a register gives 0 for a count of 32; WebAssembly's `i32.shl` and `i32.shr_u` take the count modulo 32. The healthbox lost its "Lv" glyph, and the first letter of each name showed a second time 8 pixels to its right. Patch 0006 gives what the GBA gives.
- **Function-pointer traps.** A WebAssembly function pointer is an index into a table, and `call_indirect` checks the callee's type. Three cases came up. `m4aSoundInit` calls jump table entry 35 (`SoundMainBTM`) with one argument, and the first stub took none: a signature trap, fixed in the glue's table. `decompress.c` copies its ARM decoders, the bytes between two function addresses, into a stack buffer and calls the buffer: "table index is out of bounds" at the battle's first load, fixed by patch 0003. `event_scripts.s` marks an effect command as `func + ROM_SIZE`, and a table index carries no addend: the converter refuses that by name, and patch 0002 looks the functions up in a list instead.
- **The VCOUNT wait.** `SampleFreqSet` in `m4a.c` waits until the display reaches line 159. In the module VCOUNT moves only inside `VBlankIntrWait`, so the game hung in `m4aSoundInit` before its first frame. Patch 0004 drops the wait.

- **The rename that renamed the callers.** `random.c` writes `Random32` as Thumb assembly in a naked function, which clang cannot compile for wasm32. The first build renamed it with `-DRandom32=IrvWasm_UnusedRandom32` and emptied its body, so that the glue's C `Random32` would serve every call. A `-D` rename also renames the file's own calls, the inline `Random()` among them. `RandomUniform` and the other helpers of `random.c` reached the empty copy: `RandomUniform` always returned its lower bound, and `AdvanceRandom`, called once per frame, never stepped the RNG. The review found it in the compiled object. Patch 0009 leaves the naked function out under `IRV_WASM`, the rename and the emptied body are gone, and the helpers call the glue's `Random32`. `wasm-config.ts` now refuses a define that renames a name. After the fix both streams reach END at the same frames as before, and all 13 scenes pass.

- **The sign in the shake animation's address.** `AnimShakeMonOrBattlePlatforms` (`battle_anim_normal.c`) rebuilds the address of the value it shakes from the sprite's `data[6]` and `data[7]`, two `s16`, and does not cast the low half to `u16`. At an address with bit 15 set, the sign fills the upper half with ones. The ROM's four targets lie between 0x0200018c and 0x02034e8e with bit 15 clear, and the normal module reads its own without a trap. The sanitized build of #44 moved the static data, and its first shake read out of bounds at frame 1120 of hand-made. Patch 0010 casts the low half to `u16`, as `battle_anim_mons.c` and `task.c` do; at an address with bit 15 clear the result stays the same. A search of the tree found no other such join without the cast. With patch 0010 the normal module plays all four runs with every frame equal to the baseline, and the oracle finds 48 of 48 and 682 of 682 states equal.

- **The zero divisor in the shake animations.** `VerticalShakeTwice` and `VerticalShakeLowTwice` (`pokemon_animation.c`) step through `sVerticalShakeData`, whose end row is `{-1, 0}`. On that row each divides 0 by the row's length, 0, and drops the result as it ends the animation. The ROM links libgcc's `__divsi3`, which returns 0 for 0 / 0, `0x7fffffff` for a positive numerator and `0x80000000` for a negative one, all without a fault. WebAssembly's `i32.div_s` traps on a zero divisor. The module stopped with "divide by zero" at the first send-out of a species that plays either animation: far and near Tauros in 995161, near Tyranitar in 993907, 994086 and 994176. Neither baseline stream sends out such a species, so the trap stayed hidden until stage 5 played 995161 and 993907. Patch 0011 gives 0 for a zero divisor at both sites, the GBA's result for 0 / 0. With it every frame of the four baseline runs stays equal, and every fixture reaches END in the module.

Smaller ones: `script.c` breaks out of its effect analysis with `__builtin_setjmp`, which clang refuses on wasm32 (patch 0001, libc's `setjmp`); `REG_DISPCNT` must start in forced blank as the BIOS leaves it, or the first DISPSTAT write stays buffered and VBlank never fires.

### The class nothing warns about

A shift by 32 or more is undefined in C. The GBA gives 0, WebAssembly gives the shift by the count modulo 32, and neither gcc nor clang warns when the count is a variable. Patch 0006 fixes the one case that a scene showed.

#44 built the module once with clang's shift check. `npm run wasm:build -- --compile --sanitize shift` and `-- --link --sanitize shift` compile the 385 files of the tree and the 24 of our glue and layer with `-fsanitize=shift`, link UBSan's runtime and write everything under `build/wasm/sanitize/`, beside the normal outputs. The runtime logs the file, line and column of each site the first time it fires and lets the run go on, so one run lists every site; a trap would stop at the first. `npm run wasm:run -- --against-baseline --sanitize shift hand-made 994052` plays that module. On 23.11.2026, with patch 0010 in, hand-made reached END at frame 2916 and 994052 at 40981, both refusals came at frame 31, the 13 scenes of each stream passed, and every frame of the four runs equalled the normal module's baseline. The compile took 4:17 at 2 jobs, the link 26 s and the four runs 3:01.

The check found no shift by 32 or more and no negative count on the battle path. It fires on such a shift: a probe of `1u << 32` with the same flags logged "shift exponent 32 is too large for 32-bit type 'unsigned int'". `text.c` compiles from patch 0006's copy, so its two shifts by 32 no longer occur.

It found 32 sites of the check's other half: a left shift that moves a bit into or past the sign bit of an `int`, or that shifts a negative value. C leaves those undefined too, but the count stays under 32, and the GBA's `LSL` and WebAssembly's `i32.shl` give the same 32 bits. All 32 lie on the battle path, and none changes a frame or a sound: the oracle holds the module's frames against mGBA's, and the sanitized module's frames equal the normal module's.

Our layer reports no site. Four of its files carry the check (`irv_dma.c`, `irv_mp2k_main.c`, `irv_render.c`, `irv_render_blend.c`); the others hold no shift that needs one. The run found one more bug, which no shift caused: the shake animation's address (patch 0010, above).

Division by zero is a second class. The GBA's division helpers from libgcc return a value for a zero divisor and go on. WebAssembly's integer division and remainder trap there, and its signed division traps on `INT_MIN / -1` too. Neither Emscripten 7.0.0 nor Binaryen 133 has a switch that changes this: Emscripten refuses `-sBINARYEN_TRAP_MODE=clamp`, and `wasm-opt` knows no `--trap-mode-clamp`. So `npm run wasm:build -- --link` rewrites the module after the link (`scripts/wasm-divide.ts`, #66). Each division and remainder becomes a call of its helper in our glue (`irv_wasm_divide.c`), and the helpers return what the ROM's libgcc 14.2.1 returns. By zero, a 32-bit quotient or remainder saturates by the numerator's sign. A 64-bit result by zero depends on the numerator's bit length, because libgcc's 64-bit division runs its shift loop without a zero test. The ROM links no 64-bit remainder helper and the module holds no 64-bit remainder, so those two helpers follow `__moddi3` and `__umoddi3` from the same libgcc archive. The specs run all eight helpers in the native harness against values that libgcc's own code returned. The sanitized link keeps WebAssembly's ops: that module is the tool that finds a fault, and a division that traps there is its finding. Clang's `-fsanitize=integer-divide-by-zero` logs a site and then lets the division trap, so a sanitized run names one site and stops. The game's objects hold about 490 divisions and remainders by a divisor they compute. Patch 0011 gives the GBA's result at the two sites the fixtures reached. A read of the other computed divisors in `pokemon_animation.c` found none that a battle can bring to 0.

A build without patch 0011 plays 995161 to END at frame 32711 with every frame equal to the build with it, so the rewrite alone covers both of 0011's sites. The patch stays in the series.

### Traps the GBA survives

The GBA goes on through some faults that stop the module with a trap. A visitor then reads "The game stopped during this replay. Report it with the link below." (`gameStopped` in `src/web/visitor.ts`). Division has a guard; the other classes have none.

| Class                                                                            | Guard in the module                                |
| -------------------------------------------------------------------------------- | -------------------------------------------------- |
| An integer division or remainder by 0, or `INT_MIN / -1`                         | the rewrite after the link and `irv_wasm_divide.c` |
| A call through a null or mistyped function pointer; the GBA jumps                | none                                               |
| Memory past the module's 256 MB (`scripts/wasm-link.ts`); the GBA reads open bus | none                                               |
| `unreachable` outside the assert path                                            | none                                               |

The test replays and the send-out streams reach none of these traps.

Two more differences have no guard, and a run that reaches END does not rule them out. The module maps the GBA's mirrored RAM one to one: the EWRAM and IWRAM mirrors lie inside the module's 256 MB, so a read or write through a mirror reaches another address of the module's memory without a trap. The module's call stack is Emscripten's shadow stack of 1 MB (`-sSTACK_SIZE` in `scripts/wasm-link.ts`), and the link sets no stack overflow check. Nothing guards that stack, and no run has shown whether an overflow traps or writes below it.

## What shipping would need

Two questions stood between the spike and a public build (plan D5 and D7). Each had options with a cost in builder steps.

### A platform layer we may ship

In wave 3 the module held platform files borrowed from a port with no licence, and the wave 3 gate (answer 3a) chose a layer of our own under MIT over asking that port's authors for a licence or building on mGBA's MPL-2.0 renderer and BIOS.

#43 built it in wave 4, in ten steps against the spike's estimate of five to seven. The first part replaced the BIOS calls, DMA, the interrupts, the frame driver and the renderer in five builder steps: the BIOS calls and DMA one each, the renderer three. On each state the oracle samples, our layer picks the layers, windows, effect and coefficients that mGBA's frame shows, and each pixel it draws is GBATEK's 5-bit result of that choice. The second part took five more: the functional spec of the game's sound engine, the PSG channels, the sequencer, the mixer with the swap of the sound, and a last step that took the borrowed checkout out of the build. The native harness, the oracle and the spec step account for the difference.

The module that last step built compiles the 385 tree files and the 24 files of our glue and layer, and nothing else: `npm run wasm:build` fetches no checkout, and `llvm-nm` of the linked module lists none of the names that only the borrowed files defined. The module is the same size as before that step (25,967,713 bytes, module patch 20,965,436). Both streams pass all 13 scenes and both refusals, reach END at 2916 and 40981 with every frame equal to stage 3's module, and the oracle matches 48 of 48 and 682 of 682 states. On stage 4's merged tree, at a load of 3 to 6.5, the spike e2e plays hand-made with sound at 1x (59.54 frames per second) and 2x (120.49), 994052 with sound for 5 s at 1x (59.78) and 5 s at 2x (118.57), and 994052 at fast to END at 40981 (304 frames per second on average).

### Nintendo's assets from the dump

The module patch works as the ROM patch does: the page applies it to your dump. It copies 22 % of the module's bytes from the dump and carries the other 20.1 MB itself: the compiled code, the expansion's new assets, and the retail assets that the expansion recompresses or stores in another form.

- **(a) Per-asset extraction.** The page would find each asset in the dump and place it in the module's data. The expansion recompresses graphics with its own tANS decoder (`src/decompress.c`) and stores them in other places and formats, so the build would need a generated table from the pinned sources: asset, retail offset, retail format, the module's address and format, with a spec that checks it against the dump. Assets that retail Emerald lacks (the new species, moves and their sounds) still travel in the patch. Cost: four to six steps, and the patch keeps the new assets.
- **(b) Accept the module patch as the ROM patch is accepted**, an ADR 0002 amendment (draft below). Cost: none in steps; it carries the same new and recompressed assets that `irv-emerald.bps` carries today.

## Drafts for the gate

The gate accepted both drafts on 22.11.2026 (answers 2a and 4a): the amendment now closes ADR 0002, and ADR 0009 replaces ADR 0008 for the WebAssembly build. The texts below are the drafts as the gate read them.

### Draft: ADR 0002 amended

> For pokeemerald-expansion the page may build either a ROM image or a WebAssembly module from the user's base ROM. The module patch (`irv-emerald-wasm.bps`) turns the base ROM into the module, as the patch turns it into the ROM image. The module stays in the user's tab, like the patched ROM: no server hosts or ships a module, a ROM, or a module or ROM with the patch applied. The server serves the module patch and Emscripten's glue.
>
> The module patch may carry what the ROM patch carries: the expansion's code and assets, compiled with ours, under the posture that ADR 0002 and 0007 take for the ROM patch. Any other code compiled into the module, the platform layer and the runtime libraries among it, needs a licence that lets us distribute it inside a patch.

### Draft: ADR 0008 replaced

> **Gen 3 replays are written into the game's memory before it starts.** In the WebAssembly build the worker writes a replay's instruction stream into the replay slot in linear memory after it instantiates the module and before it calls `AgbMain`. The slot keeps the layout of `rom/gen3/include/replay_slot.h`, so the page writes it through the same `writeReplaySlot`. Nothing is built per replay, and Restart starts a fresh instance with the stream again.
>
> The emulator path keeps writing the stream into the ROM image as before. Because the worker owns the game's memory, live play (roadmap 7) can write instructions and keys while the game runs.

## Rests

- The audio drift: in headless Chromium the worklet reads 2.5 to 3 % slower than the worker writes, and a fifth slower on a loaded devbox. The latency cap holds the fill at 0.2 s, and each skip back to 0.1 s cuts the sound once; at a 3 % gap that is a cut every few seconds. A resampler that follows the fill would play it without cuts. Since wave 4 the worklet waits for a reserve of 33 ms before it plays and after each dry spell, and the page counts each dry spell once.
- `include/script.h` has three inline checks that test a pointer for ROM mirror 1 (specials, `gotonative`, `callnative`). Under the module they read every pointer as unmarked, so an effect analysis stops early. That is the field path, not the battle's.
- Phones: 256 MB of fixed linear memory, a module worker, `SharedArrayBuffer` and an audio worklet. Not tried on a phone.
- Input: the page sends no keys. Live play (roadmap 7) needs the page to write them to `REG_KEYINPUT` as `wasm:run` does.
- The clock: the module's real-time clock and the shot tool's mGBA both stand still at noon on 1 January 2000. The emulator page sets no clock for its mGBA, and native mGBA follows the host's clock by default, so a scene there can show another time of day than the module.
- 2x runs the sound through a 19-tap half-band filter before it keeps every other pair (#47). After a change of pace the filter starts from an empty history, which may sound as a tick.
- Bitmap modes 3 to 5 and the prohibited modes 6 and 7: the layer fills each line with the backdrop, draws no OBJs and logs the mode once. GBATEK would draw the bitmap and the OBJs from tiles 512 to 1023. No battle file sets these modes.
- Brightening (BLDCNT mode 2): no state of either stream that the oracle sampled brightens, so the oracle's model of mGBA's arithmetic there is a guess, and only the blend specs check ours.
- The affine reference point restarts when the game writes a new value to BG2X, BG2Y, BG3X or BG3Y. A write of the same value in mid-frame leaves the point where it stands. The battle sets no affine mode.
- An interrupt that IME or IE holds back stays in IF, and the layer never delivers it later; GBATEK says the CPU takes it once both allow it. The battle path does not reach this: VBlank runs with IME forced on, VCount stays enabled, and the DMA interrupts go to `IntrDummy`.
- RL decompression and Div are not built. The module has no caller for them, and a new caller fails the link.
- ArcTan2 and the sine table follow the formulas, not the BIOS's own approximation and table. The A/B against the borrowed build hid a difference of one in Q14 behind the `>> 14`.
- The OBJ cycle budget per line follows GBATEK's counts, and no oracle state is known to reach it.
- The window edges with X1 > X2 or Y1 > Y2 read as X2 = 240 and Y2 = 160, as GBATEK says, with no wrap. The oracle saw three WIN0 ranges and no WIN1, so only the specs check this. The animations of Memento, Curse and Fake Out build WIN0H from moving values (`battle_anim_dark.c`, `battle_anim_ghost.c`, `battle_anim_effects_2.c`); an oracle run every frame across one of them would settle it.
- Nothing ties the module to `build/rom/replay-slot.json` beyond the slot's magic. A ROM rebuilt with another slot layout beside a stale module would let the page write past the module's slot; the module could export its slot's size for the page to check.
- `docs/plan.md` said the page hands the stream over instead of through the replay slot, while the ADR 0008 draft kept the slot in linear memory. The gate took the draft (ADR 0009), and the plan now says so.
- `wasm-config.ts` and `rom-config.ts` each check their config fields; one shared checker would do.
- The production build for a real host, and its headers, stay M2's work. `npm run build` with `vite preview` already serves the spike page: the e2e passed against it, with the worker and the worklet loading from `dist/assets/`.
