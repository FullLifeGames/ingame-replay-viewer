# The Gen 5 spike (#72)

Milestone 6 plays replays inside Black 2 and White 2 on a DS emulator, driven from outside (ADR 0003, ADR 0007). Before anyone builds a Gen 5 backend, #72 asked five questions: which emulator runs Black 2 in a browser and lets the page reach the game's memory, how the page gets into a battle, how instructions reach the battle client while the game decides nothing, where the battle text comes from, and which headless tool can check frames. The spike ran in wave 5, lane a, on 24 November 2026, in eleven builder steps: the plan's seven (S1 to S7), S2b (the page for the user's own speed check) and S3b (SkyEmu's web build), which the integrator added, and S8 and S9, which fixed what the lane's review found. The game is Black 2 (USA) from the user's dump. Each figure below names the step and the run log it comes from; the logs stay on the build machine.

## Verdict

The spike reached its goal. Black 2 boots from the dump in EmulatorJS's melonDS core in headless Chromium on the build machine, with no BIOS or firmware file. An input macro took the game from New Game into its first battle, Tepig against the rival's Oshawott, in pieces that S5 played from states saved under earlier versions of the macro. The final macro has not reached the battle from boot: in S9 its walk stalled before the lookout, at frame 23,270. Since #97 the page starts a trainer battle from power-on through a routine of its own instead, and reaches the action menu at frame 977 with no save (see "Into a battle"). In the battle the page holds the game's battle server, writes blocks of the game's own server commands into the player's battle adapter, and the game plays them: "Tepig used Tackle!", the move's animation, Oshawott's HP bar falling to the value the page gave, and "It's super effective!" (S6). The game decided nothing. One Tackle took Oshawott from 20 HP to 1, and in a second run Tepig used Flamethrower and Oshawott Hydro Pump, moves neither of them knows.

The proof covers one battle and one kind of moment: a move's line, its animation, an HP change and one standard line. Faints, switches, status, weather, the hit flash and the set messages stay untried. On the build machine the emulator runs far below real time, and no PC or phone figures have come back yet. A public page also waits on the licence call in "Licences" below.

## What the spike built

- `src/gen5/`: plain TypeScript that imports no DOM, no browser API and no Node module (17 files, 15 specs). It reads and checks the DS header (`nds-header.ts`), finds DS main RAM in the emulator's heap (`main-ram.ts`), plays input macros with RAM checks and a fixed clock (`macro.ts`, `route.ts`, `ram-check.ts`, `clock.ts`), packs server commands into an adapter block (`server-cmd.ts`, `adapter.ts`), finds the battle's Pokémon in RAM (`battle-mons.ts`) and builds one moment (`moment.ts`). No lint zone holds it yet (see "Open questions").
- `src/web/gen5/`: the Gen 5 page. It takes the dump through a file input, refuses anything but Black 2 (USA) version 0 with a sentence that names what it found, loads EmulatorJS, and gives the scripts a hook on `window` for frames, RAM and macros. A speed line, a device line and a "Copy figures" button serve the user's own check. The frame driver and the byte codecs have specs (S8).
- `scripts/gen5-*`: the fetch of EmulatorJS's pinned npm packages with their integrity check (`gen5-fetch.ts`), the page's servers (`gen5-serve.ts`, static with `--built`), the Chromium runs with frames, a request log and a memory log (`gen5-shot.ts`, `gen5-route.ts`, `gen5-moment.ts`), and the generator of pokebw2's numbers (`gen5-bw2*.ts`).
- The fetched emulator, the pokebw2 checkout, the generated `build/gen5/bw2.json`, the states and the frames sit in the gitignored `.cache/gen5/` and `build/gen5/`. The spike committed no ROM, no part of one, no state, no save file and no file of pokebw2. It left the Gen 3 code, its ROM files and the viewer's pages as they were; the shared files it changed are `knip.json` (one entry line) and `AGENTS.md` (one line in the project list).

### EmulatorJS's melonDS

The spike recommends this emulator for a backend's development: S1, S2, S2b, S5 and S6 ran on it, the battle among them.

- The page fetches the emulator from its own server. EmulatorJS 4.2.3 asks its CDN for `version.json` when the page's host name is `localhost` or `127.0.0.1` (`checkForUpdates` in `emulator.js`). The shot script opens the page under a `.localhost` name, where EmulatorJS skips the check, and the request log of every run lists local requests alone (S1, `gen5-boot.log` to `gen5-boot-3.log`; S2b, `gen5-built.log`). The npm package ships no `emulator.min.js` and no `emulator.min.css`, so each start logs two answers of 404 and the loader takes the plain files.
- Chromium's seven processes held 2.4 to 2.5 GB (sum of PSS) while the 512 MB dump loaded, and 1.9 to 2.0 GB after; the renderer alone held 1.74 to 1.84 GB (RSS; S1). The first frame came 29 to 56 s after the pick (S1 to S2b, `user-check.log`).
- Main RAM: the page searches the core's heap (1.22 GB) for the copy of the cartridge header that the boot code leaves at 0x023FFE00. It accepts a hit only when the dump's ARM9 bytes sit at the address the header gives for them. A single candidate passed in every run, at the same heap offset per core build, and the heap did not grow in four minutes (S2, `gen5-speed-plain.log`, `gen5-speed-plain-2.log`, `gen5-speed-thread.log`). A word written at 0x021DDFA8 on the title screen read back the same 61 and 62 frames later (`gen5-speed-plain-2.log`, `gen5-speed-thread.log`). S5 and S6 then read and wrote every value through this base.
- The page set the cross-origin isolation headers in every run. By its build file (`Makefile.emulatorjs`, `HAVE_THREADS ?= 0`) the plain core needs no `SharedArrayBuffer`; the spike read that and did not run without the headers.

### SkyEmu

SkyEmu is the MIT candidate, and the spike tried it twice.

- Native (S3): SkyEmu v5's Linux build aborts in its headless `http_server` mode about a second after start, before its HTTP server binds, on a failed assert in `sg_make_image` (`gen5-skyemu.log`, `gen5-skyemu-2.log`). That is the open upstream bug skylersaleh/SkyEmu#576: headless mode loads its theme image before the graphics setup, and the release builds keep their asserts. The spike's scripts for it never ran against a live server, and S7 removed them.
- Web (S3b): the build that web.skyemu.app served on 24.11.2026, fetched once and served from the build machine, boots the dump through its own file input in headless Chromium. Run 2 pressed nothing and ended in the opening (`s3b-run2.log`). Run 3 pressed Start twice: the first press changed nothing on screen, and the second brought the title screen (`s3b-run3.log`). It asked for three files and made no request off the machine. The page can reach the whole wasm heap: `SkyEmu.js` is a classic script, so `HEAPU8` lands on `window`. The header search finds two bases that pass both checks; which one is live stays open, and the spike wrote no word there. SkyEmu's own page writes the picked file into its in-browser file system and syncs it to IndexedDB, so a visitor would keep a 512 MB copy of the dump in site storage.
- The spike reached no battle in SkyEmu and tried no state.

## Into a battle (question 2)

Since #97 the page starts a trainer battle from power-on: no title, no menu, no save and no walk. This is the direct entry. The game runs unmodified, and a routine of ours (`rom/gen5/`) lives in the emulator's memory alone, as ADR 0007 allows for its fallback. `src/gen5/direct-entry.ts` plays the direct entry as one plan of 22 steps, and `scripts/gen5-moment.ts` runs it by default; `--entry walk` plays the older way (below).

### The direct entry

- **The takeover** (`src/gen5/direct-takeover.ts`). In the game's first frames the boot proc queues the boot screens in the proc manager behind `sGameProcManager`: `queued` is set, and `nextFunctions` and `nextParam` hold `BOOT_SCREENS_PROC_FUNCTIONS` and `sBootScreensParam`. In that frame, the one window before the manager switches, the page writes our routine, a proc table of its three functions and the order block into the battle overlay's span, which nothing uses before the battle loads. The generator checks the span apart from the two overlays the game's init loads. Then the page points `nextOverlayId`, `nextFunctions` and `nextParam` at our table and block. On the next update the manager runs our routine in the boot screens' place.
- **The park.** The routine's init calls `GameData_Create`, `BtlSetup_Create`, `ResetBtlFieldStatus` and `BtlSetup_SetTrainer1v1Single` with no trainer of the game's own list. It leaves the game data and the setup in the order block and sets its stage to parked. Its main then waits frame after frame for the go.
- **The park writes** (`src/gen5/direct-park.ts`, `src/gen5/direct-party.ts`), in the frame the routine reads parked, each through pointers from the setup's word in the block: the opponent's name and class (`TRAINER_CLASS_YOUNGSTER`), the player's name, fast text (`CONFIG_TEXT_SPEED_FAST`), the battle style (`BTL_STYLE_SINGLE` or `BTL_STYLE_DOUBLE`), the trainer battle's track (`SEQ_BGM_VS_TRAINER` into `fieldSituation.bgm`), and both parties of sealed Pokémon with their counts and slot bits. The page reads the style, the track and the counts back, then writes the go. A name longer than its field is cut, and the log says so.
- **The go.** The routine's main calls `GFL_BGSysEnableEngines`, which switches both displays on: on a normal boot the boot screens make that call, and the battle never does. It starts the setup's track with `GFL_SndBGMPlay` and replaces itself by the battle's proc through `GCTX_ProcMgrReplaceProc`. The game then starts its own trainer battle, loads the battle overlay over our routine and plays the opening to the action menu.
- **The checks.** The page compares every word of the code, the table and the block words it owns at the takeover, at the park and right before the go. A routine that finds no game data or no setup names that stage, and the run fails there.

### A Pokémon as data

The park writes each Pokémon as the bytes Black 2 keeps in a party, and the tree holds no number of that format.

- **The format, read by name at run time.** `scripts/gen5-bw2-pkm.ts` reads the layouts of `PartyPkm`, `PokeParty`, `PkmBufferChunk` and `PkmBlockA` to `PkmBlockD` (`include/pml/poke_party.h`), each block's column from the enum `PKM_DATA_BLOCK_A` to `PKM_DATA_BLOCK_D`, and from `src/system/poke_tool.c` the block order table `blockShufLUT`, the personality bits that `PML_PkmGetParamBlockCore` picks its row by, the key step of `PML_CryptoNextKey` and the bound of `PML_UtilPIDIsRare`. Constants such as `PARTY_SIZE`, the `GENDER_*` values, `LANGUAGE_ENGLISH` and `VERSION_BLACK2` come by their defines, and the species, moves, items, abilities and natures as whole lists by constant name from `generated/`. Each reader throws by name when the source loses the shape it expects. All of it lands under the key `pkm` of `build/gen5/bw2.json`.
- **The encoder.** `src/gen5/pkm-fields.ts` writes a Pokémon's fields into its plain bytes and reads them back (`plainPkm`, `readPkm`); the personality follows from the gender, the shininess, the original trainer's ID and a salt per slot (`pidFor`). `src/gen5/pkm-cipher.ts` seals the plain bytes: the checksum of the content, the blocks placed by the personality, the content ciphered under the checksum and the party part under the personality (`sealPkm`). `openPkm` gives the plain bytes back.
- **The team.** `scripts/gen5-moment-team.ts` names twelve Pokémon, six a side, by Showdown's names, at level 50. They go through `src/gen5/backend/party-mon.ts` (#106), the one way from Showdown's names to a written Pokémon: numbers through the maps of `src/gen5/backend/names.ts`, PP and stats from @pkmn/data, and `sealParties` for the sealed bytes.
- **A replay's teams.** `--replay <id>` writes the teams and trainer names of a test replay from `test/fixtures/replays/` in place of the hand team. `scripts/gen5-moment-replay.ts` builds them through `src/gen5/backend/` (`buildGen5Replay`), loaded through Vite's module runner. The option needs the direct entry and refuses `--player` and `--opponent`, and the frames carry the replay's id (`nosave-direct-<id>-*.png`). The run logs each fallback and each cut name as `team: ...`, reads both parties back by species, item and ability name, checks each front Pokémon's mon ID, and ends at the action menu.
- **The proof.** `scripts/gen5-pkm-real.test.ts` finds the party in the tracked save, opens its Tepig with a right checksum and seals it back byte for byte. It reads the species, the first move, the ball, the language, the origin, the name and the original trainer by name, and a write and read of every field changes none. Its assertions compare names and booleans.
- **No number in the tree.** The fixtures under pokebw2's names hold invented numbers in an order of their own, and `scripts/gen5-fixtures-real.test.ts` holds that (see "pokebw2's numbers in CI").

The direct entry's other numbers come the same way, by `scripts/gen5-bw2-entry.ts` under the key `entry`: the eight functions of `ENTRY_FUNCTIONS` from the ARM9's `symbols.txt`, each with the Thumb bit added; five data symbols, the ones named above among them; the constants by their defines and lists; the layouts of `GameProcManager`, `BtlSetup`, `BtlSetupTrainer`, `StrBuf`, `PokeParty`, `PartyPkm`, `PlayerInfo`, `Config` and `BtlFieldStatus`; the battle overlay's span from `ov167`'s `delinks.txt`; the room of the trainer's name from the buffer that `TrainerBattleSetup_Create` creates; and the strings' terminator `CHAR_EOM` from `src/system/printsys.c`.

### The walk, as history

Before #97 the page walked into a battle. The spike's route from New Game (`src/gen5/route.ts`) names the player IRV, picks Tepig and follows Hugh into the rival battle: 33,570 frames, 9 min 21 s at the DS's pace and about 24 minutes uncapped on the build machine, so S5 played it in pieces from the states of earlier marks, partly under earlier versions of the macro. Two runs from boot agreed on 179 marks up to frame 22,670 (`gen5-route-36.log`, `gen5-route-37.log`). From boot the final macro stalled at frame 23,270: a second talk with Hugh sent the counted walks after it elsewhere (S9, `gen5-route-39.log`).

#78 replaced that route with a save of our own before Youngster Terrell on Route 20 (`docs/gen5-save.md`): the page loads it, takes Continue and walks two tiles into his sight (`src/gen5/continue-route.ts`), 4,146 frames, 69.3 s at the DS's pace, to the action menu. The walk stays until its removal, a small fix of its own; the save also serves the real spec of a Pokémon's format.

What the page fixes for every way in:

- The clock: no core option, but melonDS reads the real-time clock through Emscripten's `Date.now`. The page sets it to noon on 1 January 2000 plus the emulated frames over 59.8261 (`src/gen5/clock.ts`), so the battle's clock showed 12:09.
- The firmware: the core boots on its defaults (name, birthday, language), and two runs agreed with them.
- Input: the page presses buttons through EmulatorJS's `simulateInput` before each emulated frame, frame-exact; no run skipped a frame.

What a visitor brings: the dump and nothing else. The direct entry needs no save and no state. ADR 0002 holds: a state counts as ROM-derived, so no state leaves the visitor's browser and no server hosts one.

## The way in (question 3)

The page writes blocks of the game's own server commands into memory where the battle client reads them, at addresses that pokebw2 gives. The moment injects no code and changes no file of the game (ADR 0007); only the battle's start runs a routine of ours ("Into a battle").

pokebw2 (fuddlesworth/pokebw2, pinned at `345b790e6000869b481b79838bb5727309f832fb`) rebuilds Black 2 and White 2 byte for byte, so its symbols are the retail addresses. `scripts/gen5-bw2.ts` reads a checkout of that commit and writes `build/gen5/bw2.json`: 26 symbols of overlay 167, both command enums, every command's argument format, the message rules, the queue size and the layouts of the structs the page touches, worked out from the C structs. Since #78 it also holds the tile of the save's trainer, found by his name, and since #97 the direct entry's numbers (key `entry`) and a Pokémon's format (key `pkm`), both in "Into a battle". Since #106 it holds what the backend names: the battle's constants (`battle.constants`), each `#define` of the weathers, a battle Pokémon's conditions and its stats and stat stages in `include/constants/battle.h`, and the mon-ID rule (`battle.monIds`): each client's first mon ID from `sClientFirstMonIds` and the count per client from `MonIDToClientID` in `src/battle/btl_main.c`, of which `GetClientIDFromMonID` is the plain inverse. `PokeCon_CreateClientParty` gives the Pokémon in party slot n the client's first ID plus n, and the generator stops when a client's IDs hold less than a party. The direct entry's numbers gain the setup flag `BTL_SETUP_FLAG_NO_BLACKOUT` (`include/system/btl_setup.h`, a shift of two literals, which the enum reader computes) and the setup's `flags` member; nothing writes the flag before #110. The key `font` holds, as a string, the characters that both of the battle view's fonts draw (fonts 0 and 2 of the font archive, `res/fonts/font/00/font.json` and `02/font.json`); the game draws "?" for any other. Since #107 the key `text` holds the labels of the battle's standard and set text banks (`res/text/system/0019.txt` and `0018.txt`), each with its line's index, which is the message ID the server sends. The key `flow` holds the damage kinds that `ServerDisplay_Damage` picks for the hit flash's `SC_DAMAGE_PLURAL` and the heal effect that `ServerControl_RecoverHPCore` shows with `SC_EFFECT_BY_POS`, both read by shape from `src/battle/btl_server_flow.c`, since pokebw2 names neither. The generator holds each line the backend sends (`src/gen5/backend/lines.ts`) to the message IDs its function puts, there or in `src/battle/handler/item_handlers.c`, and stops by the line's label when they part. The code reads every address, offset, command number and message number of pokebw2's at run time, from that file or, for a line's number, from the text bank by its label; the specs use invented numbers, and the generator stops on a layout that breaks its rules for the adapter (S8). This document names each value by its symbol; `node scripts/gen5-bw2.ts` prints the values for anyone with a checkout. A few rules of the game have no number in the file, and the code writes them out, each with its source in pokebw2 named in a comment: `sCommMode` 0 for a local battle and `returned` 0 and 1 (`btl_adapter.c`). The symbols the moment depends on:

| Symbol                          | What it is                                                                                                                    |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `sAdapters`                     | The battle adapters, one per client; the page reads the player's from here each time, since the game allocates it on its heap |
| `sCommMode`                     | 0 in a local battle                                                                                                           |
| `BattleServer_ProcSelectAction` | The server's step that waits for every client's action                                                                        |
| `BattleClient_ServerCmdLoop`    | The client's loop that plays a block of server commands                                                                       |
| `sServerCmdTable`               | The client's handler per server command                                                                                       |
| `sCmdFormats`                   | Each server command's argument format                                                                                         |

The adapter: `returned` and `isNet` share one byte as two bit-fields, `returned` in the lower bits; then `clientId`, `state` and `cmd`; then the command to the client, `sendCmd.cmd`, `sendCmd.size` and `sendCmd.data`. The generator checks the layout (S8), and the first battle's RAM confirmed every offset, the bit order included (S5).

How a block gets in: the client polls its adapter, and while `returned` reads 0 it takes `sendCmd.cmd` and `sendCmd.data`. The page writes the data, the size, `BTL_ACMD_SERVER_CMD` into both command fields, zero into the reply fields, and `returned` = 0 last, so the client never sees half a block. When the client has played the block, it sets `returned` to 1, and the page writes the next one. Inside a block every value goes high byte first, as the game's own queue writes it; the adapter's fields are little-endian. A block holds at most `BTL_SERVER_CMD_QUE_SIZE` bytes, the client's queue.

How the server is held: the page sets the player's adapter `state` to `BTL_ADAPTER_STATE_IDLE` before the first block. At the battle's start the server waits in `BattleServer_ProcSelectAction` for every client to reply; that check asks each adapter through `BtlAdapter_WaitCmd`, which has no case for the idle state and answers no. The client never reads `state`, so it takes block after block, and the server stays where it is. The page writes no server field, and the watch showed the server's step and sequence unchanged through both blocks of each run (S6, `gen5-moment-3.log`, `gen5-moment-4.log`).

One moment (`src/gen5/moment.ts`) is five commands: `SC_MOVE_MSG` (the user, the move), `SC_MOVE_ANIM` (the user's position, the target's, the move), `SC_OP_SUBTRACT_HP` or `SC_OP_ADD_HP` (the target, the difference to the given HP), `SC_UPDATE_HP_GAUGE` (the target), and, if the moment has one, `SC_MSG_STD` with a message number. The page reads the current HP from the client's copy of the battle in RAM, so the bar stops at the value given.

Which client is whose comes from the game's setup (#93). `BtlMain_SetupAloneSingle` creates both clients with `BattleClient_Create`: its `clientId` names each, and its `isAI` marks the opponent's. The generator reads both from there into `bw2.json`, and checks that the player's client is the `playerClientId` that `BtlSetup_LoadGameData` gives the setup. The near side's moments and readings go to the player's client and the far side's to the opponent's. The setup's per-client arrays (`party`, `playerInfo`, `trainers`) have indices of their own: `BtlSetup_SetTrainer1v1Single` loads the trainer at its `client`, and `BtlSetup_LoadPlayerParty` puts the player's party at the player's index. The park writes each side at the index read from there.

The first block of the known run: Tepig (battle mon 0) uses Tackle (33) on Oshawott (battle mon 12), Oshawott loses 19 HP, its bar moves, and `Bank0019_Text_ItsSuperEffective` ends the block. Move and species numbers come from @pkmn/dex, which the scripts checked against the battle's RAM (Tepig 498, Oshawott 501).

What S6 showed, in two runs from the battle's state: the client took two blocks one after the other with no button press between, and Black 2 played each with its line, its animation and its bar. A block took 271 to 486 frames, 4.5 to 8.1 s at the DS's rate, by the move's animation. The moves need the battle scene's animation setting as the game has it now; both runs animated. Writing an adapter command `SELECT_ACTION` afterwards brought the action menu back. Before the menu, the client played Hugh's own line "I won't forget the pain you just put my partner through!": the client shows a trainer's hint line once by the opponent's HP when the player selects an action (`CheckTrainerHintMsg`). A replay needs no menu, so a backend would not send `SELECT_ACTION`.

Injected code is ADR 0007's fallback, for what memory writes cannot reach. The spike needed none; the direct start (#97) is its first use, and the moment still goes in by memory writes alone.

## Battle text (question 4)

`btl_string.c` loads nine message files from the system message archive for a battle: banks 19 (standard lines), 18 (set lines, with variants for the player's, a wild and the foe's Pokémon), 16 (move lines), 20, ability names, move learning, yes and no, and the trainer lines of the Battle Subway and the PWT. The client prints a line from a message number plus its arguments, and the page picks a line the same way:

- `SC_MOVE_MSG` prints "X used Y!" from bank 16: each move has three lines, labelled `Bank0016_Text_Used…` for the player's Pokémon, `Bank0016_Text_WildUsed…` for a wild one and `Bank0016_Text_FoesUsed…` for the foe's. S6 showed "Tepig used Tackle!" and "The foe's Oshawott used Tackle!".
- `SC_MSG_STD` prints a line of bank 19 by its number and fills its placeholders from the words after it. S6 found the line by its label in pokebw2's text bank, `Bank0019_Text_ItsSuperEffective`, and the game printed "It's super effective!".
- `SC_MSG_SET` prints a line of bank 18, its number plus the variant of the Pokémon in its first argument. Untried.

So a backend picks a line by its label in the pinned sources, as Gen 3's backend checks its wording against the pinned expansion. Lines that Black 2 has no message for (Showdown's own messages, clauses, forfeits, effects of later generations) need finished text, as ADR 0005 says. How finished text reaches the screen stays open. showdown-bw2's README says it writes longer lines over lines it does not show; the spike did not try that, and injected code is the other route.

### The GPL question for a public page (N2)

The facts: EmulatorJS, its RetroArch and its melonDS are GPL-3.0. Serving them to visitors conveys them, which needs the GPL's text and the corresponding source of every file served, at the exact versions, under either reading below. The spike served them only on the build machine and over the user's private network to the user's own devices. The repository stays MIT; MIT is compatible with the GPL, as ADR 0007 reasons for a ROM built from pokebw2.

Two readings of what the Gen 5 page is:

- (a) One program. The page reaches into the emulator's heap, writes the game's memory, and drives its frames and input from the same tab. Read that way, the page and the emulator form one work, and the served page as a whole goes out under GPL-3.0's terms. Our code keeps its MIT licence in the repository, and the page names the GPL and offers the source, ours included, which the public repository already holds.
- (b) Two programs side by side. The page uses EmulatorJS's published JavaScript calls and reads memory as data, and the two form an aggregate. Read that way, only the emulator's files carry GPL duties.

The second route avoids the question: SkyEmu is MIT, and its web build runs Black 2 to the title screen. Its costs as measured: about a third of melonDS's speed on this machine; memory access shown by search only, with two candidate bases and no write proof; no battle, no server hold and no state tried. A page of our own around SkyEmu would also need SkyEmu built from source with the calls it needs exported, since the deployed build exports none for memory or states.

The spike recommends route one, EmulatorJS's melonDS, with the Gen 5 page served under reading (a): everything the spike proved runs on it, and reading (a) costs a notice and a source offer beside a public MIT repository. A choice of SkyEmu would first need a speed figure of both emulators on a real GPU, SkyEmu's write proof, and one moment of a battle in it. The call belongs to the user at the gate.

## pokebw2's numbers in CI

The user's answer to question 7 (24.11.2026, #77): commit none of pokebw2's numbers. CI fetches pokebw2 at its pin before the check, at depth 1, with no blob fetched before the checkout and a sparse tree of exactly the files in `POKEBW2_FILES` (`scripts/gen5-bw2-source.ts`). `node scripts/gen5-bw2.ts --quiet` then generates `build/gen5/bw2.json`. Its report gives the pin, the fetch time, the count of symbols it looked up and its checks, each as a line of names. The log is public, so the report prints no address, offset, value or size.

The direct start grew the list from the battle's files to 52: the boot and the proc manager, the battle's setup, the strings, the party, the player's info and the config, the boot overlays' and the battle overlay's link files, the Pokémon's format and the generated lists of species, moves, items, abilities, natures, trainer classes and tracks. A spec holds the list equal to the files the generator reads. The step still took 1 s in CI with all 52, and a fresh sparse fetch on the build machine took 2.8 s, 3.3 s with the generator: far under the 30 s that would send a committed table to a gate. #93 added a 53rd file, the battle client's header `include/battle/btl_client.h` (2 KB), for the names of `BattleClient_Create`'s parameters. #106 added the battle view's two fonts, about 330 KB each, for the characters they draw: 55 files. #107 added the set text bank `res/text/system/0018.txt` (about 90 KB), the server's flow `src/battle/btl_server_flow.c` (about 350 KB) and the item handlers `src/battle/handler/item_handlers.c` (about 190 KB), for the backend's lines and the flow's numbers: 58 files.

Six specs run on the real numbers there, and each asserts names and truth values only:

- `scripts/gen5-bw2-real.test.ts` runs the Gen 5 code on the generated file: the battle's symbols and layouts, the two clients and each side's setup index held to the setup functions at the pin, and the direct entry's functions, span, layouts and constants as relations.
- `scripts/gen5-bw2-battle-real.test.ts` holds what the backend names to the generated file: the weathers, conditions and stats it writes, each group with values of its own; the clients' mon-ID ranges apart, each holding a party; the setup flag a single bit inside `BtlSetup.flags`; and every ASCII letter and digit in both battle fonts.
- `scripts/gen5-bw2-text-real.test.ts` holds the backend's lines to the generated file: every label the backend sends in its bank, each label what its function puts at the pin, the three damage kinds apart and the heal effect an integer.
- `scripts/gen5-names-real.test.ts` holds the backend's name maps to pokebw2's lists: every Gen 5 species, move, item and ability of @pkmn has a constant of its name at its number, by the naming rule or by its game name, each accepted rename and the Hidden Power rule are still needed, and every nature has its `NATURE_<name>` constant. A failure prints Showdown's names and pokebw2's constant names.
- `scripts/gen5-pkm-real.test.ts` proves the Pokémon format on the tracked save ("A Pokémon as data"), and seals both Gen 5 OU test replays' parties, each Pokémon opening with a right checksum and reading back as written.
- `scripts/gen5-fixtures-real.test.ts` is the fixtures' guard. A fixture that keeps pokebw2's member names in pokebw2's order with natural widths ends up with the real small offsets, sizes and bit places, though no number in it was copied; two of ours once did. So every fixture under pokebw2's names holds invented numbers in an order of its own, and the guard walks each fixture beside the generated file by the same path. It fails when a field sits at its real place, its offset and bit, whatever its size, since widths of 1, 2 and 4 bytes meet in every layout; a first member at offset 0 fails only in its real size and width too. It also fails when a struct's size, a constant, a list entry, a table cell, a cipher number, an address or a bound matches. A struct's alignment alone does not count: the game's compiler gives one alignment to every struct that holds a word or a pointer. The invented C texts that the generator's specs hand to its readers sit in fixtures modules in `scripts/`, and the guard compares what the readers compute from them. It lists the paths alone. A fixture module in `src/gen5/`, `src/gen5/backend/` or `scripts/` that it neither compares nor lists as holding no number of pokebw2 fails it too.

On a machine without the file these specs skip; under CI each one's guard fails. `scripts/gen5-moment-direct-real.test.ts` and the routine's build spec skip in CI as well: CI has no ARM compiler, so it builds no routine.

When the fetch fails, the generator step fails with git's message. The check still runs, so lint and types report as usual, and the guards turn the job red. Nothing falls back to invented numbers. A committed table goes to a gate on either trigger: CI cannot fetch the pin on two runs at least a day apart, or the fetch and the generator add more than 30 s to the check job, the median of five runs against the five before.

## What a Gen 5 backend needs next

- The server commands of each turn. Since #107 a Gen 5 replay has version 2. `buildGen5Replay` cuts the battle script into actions: a move, a `cant` or a switch-in after the leads opens one, and the next one or the turn closes it. After a turn's last spacer line before `|upkeep|`, each residual line is an action of its own. Each action's commands pack into blocks named `b1`, `b2` and so on, each at most the smaller of the adapter's `sendCmd.data` and the client's queue, split between commands past that. A table in `src/gen5/backend/rules.ts` gives every event kind its rule, and tsc holds it complete: the park's intro, the game's leads, the turns, a fallback `later` that names the issue that plays the kind, or a fallback `line` for a line Black 2 lacks. Where a move's user and target stand in the game's places, `src/gen5/backend/moves.ts` and `hits.ts` send the server's own sequences, each with its function in `btl_server_flow.c` named: the move's line and its animation, a hit's HP drop and its `SC_DAMAGE_PLURAL` flash with the target's mon ID as a trailing byte, the effectiveness line, then the critical hit's line, and the lines of a miss, a failure and an immunity. A heal by Leftovers plays as the item's command, the heal's effect, the bar and the item's line. Until switches play (#108), the places hold the leads, and each event of another Pokémon is a fallback for #108. - The direct entry on the visitor's page: today `scripts/gen5-moment.ts` drives it from outside.
